## 一、交付格式（兩層規則）

### 1.1 每檔交付

**標題格式**（純文字）：

> ## 交付路徑：
> 📁 倉庫：{倉庫名稱}
> 📂 路徑：
>
> （以下用 code block）
>
> {倉庫內相對路徑}
>
> （以上 code block 結束）
>
> 📂 所屬專案：{專案名稱}
>
> ## 交付內容：
> 📄 {檔案內容(類別)}
> 🔄 交付類型：新增 / 修改 / 刪除
> 👤 編寫者：{編號}
> 📌 基於版本：（僅修改檔需要）
> （| {Unix_epoch} | {YYYY-MM-DD HH:mm}）

**路徑顯示規則**：

| 項目 | 顯示方式 |
|---|---|
| 倉庫名稱 | 純文字 |
| 路徑 | **Code Block**（方便一鍵複製） |
| 所屬專案 | 純文字 |

**路徑寫法**：一律用「**倉庫內相對路徑**」。

| 場景 | 正確 | 錯誤 |
|---|---|---|
| 所有操作（本機 / Spck / GitHub 網頁） | `docs/common/C-01-profile.md` | `AI-General/docs/common/C-01-profile.md` |

> ⚠️ **勿在路徑前加倉庫名稱**，否則會變成雙層目錄（如 `AI-General/AI-General/docs/...`）。

**檔案內容**：**必須用三反引號包裹**（附語言標示）

| 檔案 | 語言標示 |
|---|---|
| .js | js |
| .md | md |
| .json | json |
| .css | css |
| .html | html |
| .txt | text |

### 1.2 批次交付開頭

**格式**（純文字）：

> 📦 B{n}：第 {N}/{M} 批（{X} 檔）
>
> 交付時間：YYYY-MM-DD HH:mm
> Unix epoch：{10 位}
> 編寫者：{對話編號}#{回覆序號}

**對話編號格式**：{專案代碼}-{YYYYMMDD}-{專案內序號3位}（見 C-02 §9.1）

## 一點五、Base Version 標示（D-101）

**核心**：**修改檔必標 base version**（L-018 教訓）。

| # | 規則 |
|---|---|
| 1 | 交付「修改檔」時，必標「基於 #NNN 的 vX.Y.Z」 |
| 2 | 若無明確 base → 標「基於既有 vX.Y.Z」 |
| 3 | 「新增檔」不需標 base |
| 4 | 改動摘要須列「新增 / 修改 / 刪除什麼」 |

---

## 二、兩層三反引號規則（強制）

**核心**：分「外層」與「內層」。

### 2.1 外層（AI 交付時）

| 情境 | 寫法 |
|---|---|
| AI 交付任何檔案內容 | **必須用三反引號包裹** |
| 目的 | 提供「一鍵複製」按鈕 |

**禁止**：直接寫（不包裹）→ 使用者無法一鍵複製。

### 2.2 內層（md 檔案內部）

| 情境 | 寫法 |
|---|---|
| md 內展示格式 / 範例 | 引用塊（>） |
| md 內單行關鍵字 | 行內單反引號 |
| md 內結構化內容 | markdown 表格 |
| md 內真代碼 | 另存獨立檔案 |

**禁止**：md 內用三反引號。

### 2.3 內層（真代碼檔案）

| 情境 | 寫法 |
|---|---|
| .js / .html / .css 內含三反引號 | 正常 |
| .js 內若需展示含三反引號的範例 | 外層 = 內層最多 + 1 |

---

## 三、END OF FILE 格式

**格式**（用三反引號包裹）：

> /\* ═══ EOF ═══
> F: 完整路徑
> V: Unix epoch
> B: 批次號
> W: 編寫者#序號
> ═══ \*/

| 縮寫 | 全稱 |
|---|---|
| F | File |
| V | Version |
| B | Batch |
| W | Writer |

**註解符號**：

| 檔案 | 符號 |
|---|---|
| .js / .css | 斜線星號（成對） |
| .md | 斜線星號 或 HTML 註解 |
| .html | HTML 註解 |
| .json | 不支援 |
| .yml / .yaml | 井號（#） |

---

## 四、單行索引

**每批交付開頭附**：

> 📦 B32-2 [1791886800]
>
> docs/C-02-rules.md      V:1791886800 W:webapp-20261016-001#014

**編寫者格式**：{對話編號}#{回覆序號}

## 五、檔案狀態總表（取代原「本對話追蹤表」）

每次有修改點時，AI 在回覆末尾顯示此表。

**格式**：

| # | 檔案路徑 | 狀態 | 修改項 | 交付編號 |
|---|---|---|---|---|
| 1 | docs/common/C-02-rules.md | ⏳ 待交付 | 加入規則X | — |
| 2 | docs/common/C-11-terms.md | ✅ 已交付 | 加入詞彙 | webapp-20261016-001#003 |

**狀態定義**：

| 狀態 | 標記 | 意義 |
|---|---|---|
| 討論中 | 💬 | 已記錄修改項，尚未確認交付 |
| 待交付 | ⏳ | 已確認，等待交付 |
| 已交付 | ✏️ | AI 已交付，等你更新 |
| 已更新 | ✅ | 你已貼到 GitHub |
| 方案已改 | 🔄 | 需重新交付 |
| 已廢棄 | 🗑️ | 不再使用 |

**顯示時機**：

| 時機 | 動作 |
|---|---|
| 有修改點時 | 顯示 |
| 每 5 輪 | 主動回顧一次 |
| 交付前 | 逐項確認一次 |

## 六、交付類型標示

| 標示 | 含義 |
|---|---|
| （新增） | 全新檔案 |
| （修改） | 完整替換舊檔 |
| （刪除） | 刪除檔案 |
| （片段 - 違反規則） | 只給片段（例外） |

## 七、backtick 嵌套規則

| 內層最多 | 外層 |
|---|---|
| 3 個 | 4 個 |
| N 個 | N + 1 個 |

**md 檔案內**：遵守 §二（零三反引號）。

---

## 八、常見錯誤修正

| # | 錯誤 | 正確 |
|---|---|---|
| 1 | 只給 diff | 完整檔案 |
| 2 | 用「...」「同上」 | 完整列出 |
| 3 | 多檔合併 | 每檔獨立 |
| 4 | 內層三反引號 | 外層 = 內層 + 1 |
| 5 | 忘 EOF | 必加 |
| 6 | 檔案 > 800 行 | 拆檔 |
| 7 | 忘 Token 狀態 | 見 C-02 §零點五 |
| 8 | 未標交付類型 | 必標 |
| 9 | 未附追蹤表 | 必附 |
| 10 | 未附單行索引 | 必附 |
| 11 | Version 用舊制 | 用 Unix epoch |
| 12 | 未標編寫者 | 必標 |
| 13 | md 內用三反引號 | 改引用塊 |
| 14 | 交付時未用三反引號包裹 | 必須包裹 |
| 15 | 修改檔未標 base version | 必標（D-101） |
| 16 | 未讀當前版本就重寫 | 先讀（D-100） |
| 17 | **路徑前誤加倉庫名稱** | **只用倉庫內相對路徑（L-025）** |
| 18 | 未標所屬專案 | 必標 |
| 19 | 交付不完整（以 Token 為理由偷懶） | 必完整（C-02 §零） |
| 20 | 路徑未用 code block | 路徑一律 code block（L-024） |

## 九、多批交付

| 檔案行數 | 每批檔數 |
|---|---|
| < 200 行 | 3~4 檔 |
| 200~400 行 | 2 檔 |
| > 400 行 | 1 檔 |

## 十、更新清單流程

| 步驟 | AI 動作 |
|---|---|
| 1 | 列「所有已交付批次」 |
| 2 | 問「已部署到哪個批次？」 |
| 3 | 列「該批次後所有最新版檔案」 |

**格式**：B{批次} ← 路徑（V:epoch W:writer）

## 十二、交付前自我檢查

### 檔案層

| 檢查項 |
|---|
| 路徑為倉庫內相對路徑（無倉庫名前綴） |
| 內容完整 |
| 內容用三反引號包裹（外層） |
| 含 EOF（F/V/B/W） |
| md 內零三反引號（內層） |
| 交付類型已標示 |
| 所屬專案已標示 |
| 編寫者已標 |
| 修改檔已標 base version（D-101） |
| 已先讀當前版本（D-100） |

### 方案層

| 檢查項 |
|---|
| 已跑 5 問自檢 |
| 已掃描實際檔數 |
| 交付摘要含最小改動對比 |
| 能解釋「為何不是 N-1」 |

### 追蹤層

| 檢查項 |
|---|
| 單行索引已附 |
| 檔案狀態總表已附 |
| Token 狀態已顯示 |

## 十三、交付摘要必附 4 欄位

| 欄位 | 內容 |
|---|---|
| 改動檔案數 | N |
| 最小改動路徑 | 如何得出 |
| 為何不是 N-1 | 為何不能再少 |
| 所屬專案 | AI 對話系統 / 家庭 webapp / 其他 |
