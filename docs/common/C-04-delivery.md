## 一、交付格式（兩層規則）

### 1.1 每檔交付

**標題格式**（純文字）：

> ## 交付路徑：
> 📁 倉庫：{倉庫名稱}
> 📂 路徑：
>
> （以下用 code block）
>
> {倉庫內相對路徑}
>
> （以上 code block 結束）
>
> 📂 所屬專案：{專案名稱}
>
> ## 交付內容：
> 📄 {檔案內容(類別)}
> 🔄 交付類型：新增 / 修改 / 刪除
> 👤 編寫者：{編號}
> 📌 基於版本：（僅修改檔需要）
> （| {Unix_epoch} | {YYYY-MM-DD HH:mm}）

**路徑顯示規則**：

| 項目 | 顯示方式 |
|---|---|
| 倉庫名稱 | 純文字 |
| 路徑 | **Code Block**（方便一鍵複製） |
| 所屬專案 | 純文字 |

**路徑寫法**：一律用「**倉庫內相對路徑**」。

| 場景 | 正確 | 錯誤 |
|---|---|---|
| 所有操作（本機 / Spck / GitHub 網頁） | `docs/common/C-01-profile.md` | `AI-General/docs/common/C-01-profile.md` |

> ⚠️ **勿在路徑前加倉庫名稱**，否則會變成雙層目錄（如 `AI-General/AI-General/docs/...`）。

**檔案內容**：**必須用三反引號包裹**（附語言標示）

| 檔案 | 語言標示 |
|---|---|
| .js | js |
| .md | md |
| .json | json |
| .css | css |
| .html | html |
| .txt | text |

### 1.2 批次交付開頭

**格式**（純文字）：

> 📦 B{n}：第 {N}/{M} 批（{X} 檔）
>
> 交付時間：YYYY-MM-DD HH:mm
> Unix epoch：{10 位}
> 編寫者：{對話編號}#{回覆序號}

**對話編號格式**：{專案代碼}-{YYYYMMDD}-{專案內序號3位}（見 C-02 §9.1）

## 一點五、Base Version 標示（D-101）

**核心**：**修改檔必標 base version**（L-018 教訓）。

| # | 規則 |
|---|---|
| 1 | 交付「修改檔」時，必標「基於 #NNN 的 vX.Y.Z」 |
| 2 | 若無明確 base → 標「基於既有 vX.Y.Z」 |
| 3 | 「新增檔」不需標 base |
| 4 | 改動摘要須列「新增 / 修改 / 刪除什麼」 |

---

## 二、兩層三反引號規則（強制）

**核心**：分「外層」與「內層」。

### 2.1 外層（AI 交付時）

| 情境 | 寫法 |
|---|---|
| AI 交付任何檔案內容 | **必須用三反引號包裹** |
| 目的 | 提供「一鍵複製」按鈕 |

**禁止**：直接寫（不包裹）→ 使用者無法一鍵複製。

### 2.2 內層（md 檔案內部）

| 情境 | 寫法 |
|---|---|
| md 內展示格式 / 範例 | 引用塊（>） |
| md 內單行關鍵字 | 行內單反引號 |
| md 內結構化內容 | markdown 表格 |
| md 內真代碼 | 另存獨立檔案 |

**禁止**：md 內用三反引號。

### 2.3 內層（真代碼檔案）

| 情境 | 寫法 |
|---|---|
| .js / .html / .css 內含三反引號 | 正常 |
| .js 內若需展示含三反引號的範例 | 外層 = 內層最多 + 1 |

---

## 三、END OF FILE 格式

**格式**（用三反引號包裹）：

> /\* ═══ EOF ═══
> F: 完整路徑
> V: Unix epoch
> B: 批次號
> W: 編寫者#序號
> ═══ \*/

| 縮寫 | 全稱 |
|---|---|
| F | File |
| V | Version |
| B | Batch |
| W | Writer |

**註解符號**：

| 檔案 | 符號 |
|---|---|
| .js / .css | 斜線星號（成對） |
| .md | 斜線星號 或 HTML 註解 |
| .html | HTML 註解 |
| .json | 不支援 |
| .yml / .yaml | 井號（#） |

---

## 四、單行索引

**每批交付開頭附**：

> 📦 B32-2 [1791886800]
>
> docs/C-02-rules.md      V:1791886800 W:webapp-20261016-001#014

**編寫者格式**：{對話編號}#{回覆序號}

## 五、檔案狀態總表（取代原「本對話追蹤表」）

每次有修改點時，AI 在回覆末尾顯示此表。

**格式**：

| # | 檔案路徑 | 狀態 | 修改項 | 交付編號 |
|---|---|---|---|---|
| 1 | docs/common/C-02-rules.md | ⏳ 待交付 | 加入規則X | — |
| 2 | docs/common/C-11-terms.md | ✅ 已交付 | 加入詞彙 | webapp-20261016-001#003 |

**狀態定義**：

| 狀態 | 標記 | 意義 |
|---|---|---|
| 討論中 | 💬 | 已記錄修改項，尚未確認交付 |
| 待交付 | ⏳ | 已確認，等待交付 |
| 已交付 | ✏️ | AI 已交付，等你更新 |
| 已更新 | ✅ | 你已貼到 GitHub |
| 方案已改 | 🔄 | 需重新交付 |
| 已廢棄 | 🗑️ | 不再使用 |

**顯示時機**：

| 時機 | 動作 |
|---|---|
| 有修改點時 | 顯示 |
| 每 5 輪 | 主動回顧一次 |
| 交付前 | 逐項確認一次 |

## 六、交付類型標示

| 標示 | 含義 |
|---|---|
| （新增） | 全新檔案 |
| （修改） | 完整替換舊檔 |
| （刪除） | 刪除檔案 |
| （片段 - 違反規則） | 只給片段（例外） |

## 七、backtick 嵌套規則

| 內層最多 | 外層 |
|---|---|
| 3 個 | 4 個 |
| N 個 | N + 1 個 |

**md 檔案內**：遵守 §二（零三反引號）。

## 八、常見錯誤修正

| # | 錯誤 | 正確 |
|---|---|---|
| 1 | 只給 diff | 完整檔案 |
| 2 | 用「...」「同上」 | 完整列出 |
| 3 | 多檔合併 | 每檔獨立 |
| 4 | 內層三反引號 | 外層 = 內層 + 1 |
| 5 | 忘 EOF | 必加 |
| 6 | 檔案 > 800 行 | 拆檔 |
| 7 | 忘 Token 狀態 | 見 C-02 §零點五 |
| 8 | 未標交付類型 | 必標 |
| 9 | 未附追蹤表 | 必附 |
| 10 | 未附單行索引 | 必附 |
| 11 | Version 用舊制 | 用 Unix epoch |
| 12 | 未標編寫者 | 必標 |
| 13 | md 內用三反引號 | 改引用塊 |
| 14 | 交付時未用三反引號包裹 | 必須包裹 |
| 15 | 修改檔未標 base version | 必標（D-101） |
| 16 | 未讀當前版本就重寫 | 先讀（D-100） |
| 17 | 路徑前誤加倉庫名稱 | 只用倉庫內相對路徑（L-025） |
| 18 | 未標所屬專案 | 必標 |
| 19 | 交付不完整（以 Token 為理由偷懶） | 必完整（C-02 §零） |
| 20 | 路徑未用 code block | 路徑一律 code block（L-024） |
| 21 | 未執行兩階段確認 | 必先問「確認完整」 |

## 十二、交付前自我檢查與強制勾選

**核心**：**每次交付完整檔案時，AI 必須在回覆末尾輸出完整的檢查表，並將所有項目標記為 ✅。**
這用來防止 AI 在長對話或 Token 不足時，偷偷刪減內容或跳過步驟。

### 檢查表（交付時必附）

| 檢查項目 | 狀態 |
|---|---|
| 1. 路徑為倉庫內相對路徑（無倉庫名前綴） | ✅ |
| 2. 內容完整，無「前略」、「同上」等省略字眼 | ✅ |
| 3. 內容用三反引號包裹（外層） | ✅ |
| 4. 含 EOF（F/V/B/W） | ✅ |
| 5. md 內零三反引號（內層） | ✅ |
| 6. 交付類型已標示 | ✅ |
| 7. 所屬專案已標示 | ✅ |
| 8. 編寫者已標 | ✅ |
| 9. 修改檔已標 base version（D-101） | ✅ |
| 10. 已先讀當前版本（D-100） | ✅ |
| 11. 已跑 5 問自檢 | ✅ |
| 12. 已掃描實際檔數 | ✅ |
| 13. 單行索引已附 | ✅ |
| 14. 檔案狀態總表已附 | ✅ |
| 15. Token 狀態已顯示 | ✅ |
| 16. 已執行兩階段確認（先問「確認完整」） | ✅ |

## 十六、兩階段確認機制（D-162）

**核心**：交付檔案後，必須經過「確認完整 → 提示貼上 → 等待已更新」三道手續，禁止跳步。

| 階段 | AI 動作 | 等待使用者回覆 |
|---|---|---|
| 第一階段 | 輸出完整檔案內容，並問「**請確認：內容是否完整？**」 | 使用者回覆「**確認完整**」 |
| 第二階段 | 提示「請貼到 {路徑}，完成後回覆『已更新』」 | 使用者回覆「**已更新**」 |
| 第三階段 | 標記檔案為 ✅，繼續後續流程 | — |

**禁止**：
1. 在第一階段直接叫使用者貼上。
2. 在使用者未回「已更新」前，進入下一個檔案的交付。
