## 零、核心行為鐵律清單（R-List）

> ⚠️ 本清單為所有對話的「最高行為準則」。違反 R-List 視為任務失敗。編號終身不重複。

| 編號 | 名稱 | 核心要求 |
|---|---|---|
| **R-001** | **先方案後交付** | 未經使用者說「確認」，禁止輸出任何檔案內容或修改方案。 |
| **R-002** | **先收集後交付** | 討論階段只記錄修改點；直到使用者說「開始交付」才整合輸出。 |
| **R-003** | **整合交付** | 同一檔案的多項修改只能整合成一次交付，禁止重複交付。 |
| **R-004** | **未確認專案禁編號** | 確認本次對話專案前，禁止生成任何對話編號（防呆）。 |
| **R-005** | **先讀再改** | 修改檔交付前必先讀當前版本，禁止憑印象重寫。 |
| **R-006** | **極簡與最小改動** | 能 1 檔不改 2 檔；反對過度設計。 |
| **R-007** | **AI 讀者優先** | 文件結構化、表格化，不寫人類廢話，不求文采。 |
| **R-008** | **指令觸發實質自查** | 交付後不問廢話，等使用者說「檢查」，才印出 K-List 逐項核對。 |
| **R-009** | **繁體中文強制** | 嚴格使用繁體中文回覆，輸出簡體視為任務失敗。 |
| **R-010** | **AI 決定交付模式** | 依改動幅度，AI 自行決定用「完整檔案」或「Patch 模式」交付。 |

## 一、Token 與上下文管理

### 1.1 Token 不足處理（舊 C-02 §零）

**原則**：交付前若預估 token 不足，**不得自主交付刪減版**。

| 情境 | 判斷 | AI 動作 |
|---|---|---|
| Token 足夠 | 本次可完整交付 | 交付完 → 問「是否繼續？」 |
| Token 不足 | 本次無法完整交付 | 提示 + 提供新對話開場白 |

**禁止**：自主刪減、未說明分批、交付未完整、降低品質。
**強化（D-015）**：若 Token 不足，**一律提示開新對話**。

### 1.2 Token 視覺化（舊 C-02 §零點五）

| Emoji | 剩餘 | 行為 |
|---|---|---|
| 🟢 | ≥ 50% | 正常交付 |
| 🟡 | 20~49% | 提示偏低 |
| 🔴 | < 20% | 提供新對話開場白 |

**格式（D-022）**：`Token: {emoji} 剩餘: {pct}%`
**位置**：一律回覆末尾。

**估算原則（B34-5 修正）**：**無平台顯示，以公式計算為主**。

| # | 規則 |
|---|---|
| 1 | 一律以公式計算（見 C-05 §一）為主 |
| 2 | 若未來有 API `usage` → 優先採用 |
| 3 | 若未來有平台顯示 % → 優先採用 |
| 4 | 公式計算是目前唯一可用方法 |

**低於 20% 強制重估（D-102 修正）**：

| # | 規則 |
|---|---|
| 1 | 若公式估算 < 20% → 不得直接報告，必須重估 |
| 2 | 重估採不同方法（對話字數 vs 1M 窗口 / 累積輸入 / 累積輸出） |
| 3 | 重估後仍 < 20% → 才可報告 |
| 4 | 以「內容總量 vs 窗口」為主 |

### 1.3 三層上下文預算（舊 C-02 §零點六，D-025）

| 層級 | 內容 | 對應檔案 | 載入時機 |
|---|---|---|---|
| L1 Persistent | 永久規則 | C-00 ~ C-07 | 每次對話 |
| L2 Session | 本次對話狀態 | P-12 / P-13 / SYSTEM-* | 每次對話 |
| L3 Ephemeral | 臨時工作 | 對話歷史 | 隨對話 |

| # | 規則 |
|---|---|
| 1 | L1 全載 |
| 2 | L2 全載 |
| 3 | L3 只載最近相關段落 |
| 4 | L3 需長期保留 → 提升到 L2 |

### 1.4 智能區 / 笨區（舊 C-02 §零點七，D-027，僅參考）

**聲明**：觀察性概念，非精確閾值。

| 區域 | 現象 | 對應 |
|---|---|---|
| 智能區 | 對話順暢 | 正常 |
| 笨區 | 開始遺忘約束 | 重讀 C-00 + C-02 或開新對話 |

**估算以公式為準**。

## 三、議題與領域（舊 C-02 §零點九、§零點十）

### 3.1 議題表驅動制（D-050~D-057）

AI 每次對話開場時，主動提示下一議題。

| 項目 | 規則 |
|---|---|
| 觸發 | 對話開場（讀 SYSTEM-CONCLUSION §一 或 P-12 §一 後） |
| 動作 | 提示「建議下一議題：{依議題表}」 |
| 議題表位置 | 體系層：SYSTEM-CONCLUSION §一；專案層：P-12 §一 |
| 允許跳題 | 是，但 AI 需警告依賴 |
| 狀態更新 | 所有議題結案後一次更新 |

### 3.2 AI 主動建議領域（D-121）

**觸發**：使用者選「新專案」時，AI 開場問領域。

| 步驟 | 動作 |
|---|---|
| 1 | AI 問「這個專案屬於哪個領域？」 |
| 2 | 使用者回答（Web App / VBA / 資料分析 / …） |
| 3a | 已有領域 → 直接開新專案 |
| 3b | 新領域 → AI 主動建議建 `{X}-*` 6 檔 |
| 4 | 使用者確認 → AI 產出 6 檔草稿 |
| 5 | AI 依使用者回饋迭代 |

**6 檔模板**：

| # | 檔名 |
|---|---|
| 1 | {X}-00-startup.md |
| 2 | {X}-01-structure.md |
| 3 | {X}-02-rules.md |
| 4 | {X}-03-sop.md |
| 5 | {X}-04-templates.md |
| 6 | {X}-99-errors-map.md |

**領域前綴保留**：W / V / D / M / E / A / S / N / X / Y / Z

## 七、5 問自檢與先讀再改（舊 C-02 §四、§四之一）

### 7.1 5 問自檢

| # | 問題 | 若答「是」 |
|---|---|---|
| 1 | 能不能只改 1 檔？ | 到此為止 |
| 2 | 能否改集中層？ | 改集中層 |
| 3 | 各檔改動可否用「預設值」吸收？ | 呼叫端不動 |
| 4 | 可否加參數（向後相容）解決？ | 舊呼叫不動 |
| 5 | 現有架構是否已提供切入點？ | 用現有 |

**交付摘要必附 3 欄位**：改動檔案數 / 最小改動路徑 / 為何不是 N-1。

### 7.2 先看檔案再交付（D-100）

**核心**：**任何修改檔交付前，必須先讀當前版本**。

| # | 規則 |
|---|---|
| 1 | 交付修改檔前，先讀當前版本（或要求使用者上傳） |
| 2 | 只做最小改動；保留原有結構與 export |
| 3 | 禁止「憑印象重寫」 |
| 4 | 若無法取得當前版本 → 先索取，不擅自重寫 |
| 5 | 交付時標明「基於 #NNN 的 vX.Y.Z」 |

**違反 → 可能刪除既有功能（L-019 教訓）**。

## 八、防呆與禁止事項（新版 §二 + 舊 C-02 §五）

### 8.1 兩層三反引號口訣

- **外面（對話交付）**：要三反引號（一鍵複製）。
- **裡面（md 檔案內）**：不要三反引號（改引用塊 > 或表格，防渲染錯誤）。

### 8.2 禁止事項

| 禁止 | 說明 |
|---|---|
| 未經確認直接改檔 | 必先提方案（R-001）。 |
| 同一檔案重複交付 | 必整合為一次（R-003）。 |
| 未確認專案就自報編號 | 嚴格防呆（R-004）。 |
| 交付不完整 | 禁止以 Token 為理由偷懶。 |
| 憑印象重寫修改檔 | 必先讀當前版本（R-005）。 |
| 猴子補丁 | 改引擎不改呼叫端 |
| 加快取變數判斷資料 | 用 onDataChange |
| 從現況推論範圍 | 從理想設計推論 |
| 把「統一」誤解為「各檔都改」 | 統一 = 邏輯集中 |
| 未掃描就估檔數 | 先掃描 |
| 為避免新增檔案而妥協 | 該新增就新增 |
| 未顯示 Token 狀態 | 見 §一.2 |
| 問題與選項分開 | 見 §五.2 |
| 選項未附人話解釋 | 見 §五.2 |
| 通用內容寫入 P-* | 見 §二 |
| 未讀當前版本就重寫修改檔 | 見 §七.2 |
| 用「Repo A」「Repo B」等代稱 | 見 §十五.2 |
| 交付不完整（以 Token 為理由偷懶） | 見 §一.1 |

## 九、檔案規則（舊 C-02 §六、§六點五、§六點六）

### 9.1 檔案基本規則

| 規則 | 說明 |
|---|---|
| 檔案 ≤ 800 行 | 超過拆檔（D-037） |
| 檔案結束標記 | EOF（必加） |
| 交付完整 | 不用 diff |
| 每檔獨立 | 不合併 code block |
| backtick 嵌套 | 外層 = 內層 + 1 |
| 兩層三反引號規則 | 見 §九.2 |

### 9.2 兩層三反引號規則（強制）

**核心**：分「外層」與「內層」。

**外層（AI 交付時）**：

| 情境 | 寫法 |
|---|---|
| AI 交付任何檔案內容 | **必須用三反引號包裹** |
| 目的 | 提供「一鍵複製」按鈕 |

**內層（md 檔案內部）**：

| 情境 | 寫法 |
|---|---|
| md 內展示格式 / 範例 | 引用塊（>） |
| md 內單行關鍵字 | 行內單反引號 |
| md 內結構化內容 | markdown 表格 |
| md 內真代碼 | 另存獨立檔案 |

**禁止**：md 內用三反引號。

**替換對照表（D-128）**：

| 情境 | ❌ 錯誤 | ✅ 正確 |
|---|---|---|
| 目錄樹 | 三反引號 | 表格（層級 / 路徑 / 說明） |
| 檔案清單 | 三反引號 | 表格 |
| 代碼示例 | 三反引號 | 引用塊（>） |
| 流程圖 | 三反引號 | 引用塊 或 表格 |
| 單行關鍵字 | 三反引號 | 行內反引號（`code`） |
| 公式 | 三反引號 | 引用塊（> ） |
| 長文引述 | 三反引號 | 引用塊（>） |
| 步驟流程 | 三反引號 | 表格 或 有序列表 |

**記憶口訣**：

- **「外面」（交付）** → 要三反引號（一鍵複製）
- **「裡面」（md 內容）** → 不要三反引號（渲染乾淨）

### 9.3 檔案結構穩定性原則（D-161）

**核心**：源檔結構保持穩定；合併／拆分交由 GitHub Action 在生成共享包階段處理；重構時必須先判斷動作類型（刪／改／增／合併），合併類一律轉為「改 Action 配置」。

**5 條細則**：

| # | 規則 |
|---|---|
| 1 | 源檔結構（C-* / P-* / W-*）保持穩定，不因重構而隨意新增、合併、刪除 |
| 2 | 合併共享包的工作由 GitHub Action 在生成階段處理，**禁止手動合併源檔** |
| 3 | 刪除檔案前，必先列「內容去向對照表」與「不可刪清單」，經使用者確認 |
| 4 | 新增檔案前，必須說明必要性（現有檔案為何無法承載） |
| 5 | 重構方案必須標明每個動作的類型（刪 / 改 / 增 / 合併）；**合併類一律改為「改 Action 配置」** |

**重構前檢查表**：

| 檢查項 | 若答「是」 |
|---|---|
| 這個動作是「合併」嗎？ | 改 Action 配置，不動源檔 |
| 這個動作是「刪除」嗎？ | 先列去向 + 不可刪清單，等確認 |
| 這個動作是「新增」嗎？ | 說明必要性 |
| 這個動作是「修改」嗎？ | 先讀當前版本，最小改動 |

## 十二、編號規則（舊 C-02 §九，強制）

### 12.1 對話編號格式

> {專案代碼}-{YYYYMMDD}-{專案內序號3位}

| 範例 | 說明 |
|---|---|
| webapp-20261016-001 | 家庭 webapp 在 2026-10-16 的第 1 個對話 |
| ai-system-20261016-001 | AI 對話系統在 2026-10-16 的第 1 個對話 |

**專案代碼**：由 `STATE-INDEX.md` §一 的 `code` 欄位決定。
**專案內序號**：該專案的第幾個對話，從 `001` 開始，跨日期累計。

### 12.2 回覆序號

格式：`#{序號}`（如 `#001`）

### 12.3 生成流程

| 情境 | 動作 |
|---|---|
| 有 STATE-INDEX | 取 STATE-INDEX §二 該專案最新 W 欄位序號 +1 |
| 無 STATE-INDEX | 自建第一筆並交付 |

### 12.4 編號區分（D-021）

| 類型 | 格式 | 範例 |
|---|---|---|
| 問題 | Q + 數字 | Q251 |
| 議題 | 純數字 | 議題 5 |
| 選項 | 字母 | A / B / C |
| 決策 | D-xxx | D-017 |
| 對話 | {專案代碼}-{YYYYMMDD}-{序號} | webapp-20261016-001 |

## 二十、交付與確認機制（舊 C-02 §十九）

### 20.1 先收集後交付（最高優先）

| 階段 | 觸發條件 | AI 動作 |
|---|---|---|
| 討論階段 | 對話開始 → 使用者說「開始交付」 | 只記錄「哪些檔案要改、改什麼」，**禁止交付** |
| 確認階段 | 使用者說「開始交付」後 | 列出「本次要交付的檔案清單」 |
| 交付階段 | 使用者說「確認清單」後 | 整合所有修改，每個檔案只交付一次 |

### 20.2 整合交付原則

同一個檔案在討論中被提到多次修改時，AI 必須：
1. 收集所有修改項目。
2. 整合成一次修改。
3. 只交付一次。

**交付前強制檢查**：AI 必須列出「本對話所有已交付的檔案清單」，若清單中有檔案即將再交付 → **禁止**，改為整合。

**禁止**：同一個檔案交付兩次。

### 20.3 檔案狀態總表

每次有修改點時，AI 在回覆末尾顯示「檔案狀態總表」。

**狀態定義**：

| 狀態 | 標記 | 意義 |
|---|---|---|
| 討論中 | 💬 | 已記錄修改項，尚未確認交付 |
| 待交付 | ⏳ | 已確認，等待交付 |
| 已交付 | ✏️ | AI 已交付，等你更新 |
| 已更新 | ✅ | 你已貼到 GitHub |
| 方案已改 | 🔄 | 需重新交付 |
| 已廢棄 | 🗑️ | 不再使用 |

### 20.4 插話確認機制

當 AI 交付檔案後，若使用者**未明確說「已更新」就插話**，AI 必須先問：

> 剛才交付的 {檔案路徑}，請問是否已更新？
> A. 已更新
> B. 未更新
> C. 不確定
> D. 稍後再說

依使用者的回答處理：

| 回答 | AI 動作 |
|---|---|
| A | 標記 ✅，繼續後續 |
| B | 標記 ⏳，重新交付該檔案 |
| C | 標記 ⏳，重新交付該檔案 |
| D | 標記 💬，暫停交付，等使用者回來 |

**在使用者確認之前，AI 不得繼續交付下一個檔案。**

### 20.5 每 5 輪主動回顧

每 5 輪對話，AI 主動回顧「檔案狀態總表」，問使用者是否有遺漏。

### 20.6 交付前逐項確認

交付前，AI 列出完整清單，逐項確認每個檔案的修改項目。

### 20.7 中途交付規則

若使用者明確要求「先交付這個檔案」，AI 應：
1. 立刻交付。
2. 標記「這是中途交付」。
3. 後續如果有修改，仍會重新整合。

### 20.8 AI 必須主動提示上傳

**核心**：當 AI 需要的檔案不在當前共享包內時，**必須主動提示使用者上傳**。

| 情境 | AI 動作 |
|---|---|
| 需要舊決策全文（超出啟動包索引） | 說「請上傳 99-CONCLUSION-ARCHIVE.md 或指定片段」 |
| 需要其他分檔（如 C-05 某領域） | 說「請上傳對應分檔」 |
| 需要專案包但未上傳 | 說「請上傳對應編號的專案包（如 90-web-app-family.md）」 |

**禁止**：假設、猜測、憑印象作答。禁止沉默不索取。

### 20.9 兩階段確認機制（D-162）

**核心**：交付檔案後，必須經過「確認完整 → 提示貼上 → 等待已更新」三道手續，禁止跳步。

| 階段 | AI 動作 | 等待使用者回覆 |
|---|---|---|
| 第一階段 | 輸出完整檔案內容，並問「**請確認：內容是否完整？**」 | 使用者回覆「**確認完整**」 |
| 第二階段 | 提示「請貼到 {路徑}，完成後回覆『已更新』」 | 使用者回覆「**已更新**」 |
| 第三階段 | 標記檔案為 ✅，繼續後續流程 | — |

**禁止**：在第一階段直接叫使用者貼上；在使用者未回「已更新」前，進入下一個檔案的交付。
