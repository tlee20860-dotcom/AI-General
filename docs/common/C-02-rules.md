## 零、Token 不足處理

**原則**：交付前若預估 token 不足，**不得自主交付刪減版**。

| 情境 | 判斷 | AI 動作 |
|---|---|---|
| Token 足夠 | 本次可完整交付 | 交付完 → 問「是否繼續？」 |
| Token 不足 | 本次無法完整交付 | 提示 + 提供新對話開場白 |

**禁止**：自主刪減、未說明分批、交付未完整、降低品質。

**強化（D-015）**：若 Token 不足，**一律提示開新對話**。

## 零點五、Token 視覺化

| Emoji | 剩餘 | 行為 |
|---|---|---|
| 🟢 | ≥ 50% | 正常交付 |
| 🟡 | 20~49% | 提示偏低 |
| 🔴 | < 20% | 提供新對話開場白 |

**格式（D-022）**：`Token: {emoji} 剩餘: {pct}%`

**位置**：一律回覆末尾。

**估算原則（D-099）**：**以平台顯示 % 為準**；無平台顯示 → 不自行報具體 %。

**低於 20% 強制重估（D-102）**：

| # | 規則 |
|---|---|
| 1 | 若估算 < 20% → 不得直接報告，必須重估 |
| 2 | 重估採不同方法（窗口佔用 / 累積計費 / 平台顯示） |
| 3 | 重估後仍 < 20% → 才可報告 |
| 4 | 無平台顯示 → 以「內容總量 vs 窗口」為主 |

## 四、5 問自檢

| # | 問題 | 若答「是」 |
|---|---|---|
| 1 | 能不能只改 1 檔？ | 到此為止 |

**核心**：**任何修改檔交付前，必須先讀當前版本**。

| # | 規則 |

| 2 | 只做最小改動；保留原有結構與 export |
| 3 | 禁止「憑印象重寫」 |
| 4 | 若無法取得當前版本 → 先索取，不擅自重寫 |
| 5 | 交付時標明「基於 #NNN 的 vX.Y.Z」 |

**違反 → 可能刪除既有功能（L-019 教訓）**。

## 六點五、兩層三反引號規則（強制）

**核心**：分「外層」與「內層」。

### 6.5.1 外層（AI 交付時）

| 情境 | 寫法 |
|---|---|
| AI 交付任何檔案內容 | **必須用三反引號包裹** |
| 目的 | 提供「一鍵複製」按鈕 |

### 6.5.2 內層（md 檔案內部）

| 情境 | 寫法 |
|---|---|
| md 內展示格式 / 範例 | 引用塊（>） |
| md 內單行關鍵字 | 行內單反引號 |
| md 內結構化內容 | markdown 表格 |
| md 內真代碼 | 另存獨立檔案 |

**禁止**：md 內用三反引號。

### 6.5.3 內層（真代碼檔案）

| 情境 | 寫法 |
|---|---|
| .js / .html / .css 內含 ``` | 正常 |
| .js 內含 ``` 範例 | 外層 = 內層 + 1 |

### 6.5.4 替換對照表（D-128）

| 情境 | ❌ 錯誤 | ✅ 正確 |
|---|---|---|
| 目錄樹 | 三反引號 | 表格（層級 / 路徑 / 說明） |
| 檔案清單 | 三反引號 | 表格 |
| 代碼示例 | 三反引號 | 引用塊（>） |
| 流程圖 | 三反引號 | 引用塊 或 表格 |
| 單行關鍵字 | 三反引號 | 行內反引號（`code`） |
| 公式 | 三反引號 | 引用塊（> ） |
| 長文引述 | 三反引號 | 引用塊（>） |
| 步驟流程 | 三反引號 | 表格 或 有序列表 |

### 6.5.5 記憶口訣

- **「外面」（交付）** → 要 ```（一鍵複製）
- **「裡面」（md 內容）** → 不要 ```（渲染乾淨）

### 十三之一、Repo 用實際名稱（D-133）

**核心**：**提到 repo 時，一律用實際名稱**，不得用「Repo A」「Repo B」等代稱。

## 十九、交付與確認機制

### 19.1 先收集後交付（最高優先）

| 階段 | AI 動作 |
|---|---|
| 討論階段 | 只記錄「哪些檔案要改、改什麼」，**禁止交付** |
| 確認階段 | 討論結束，列出「本次要交付的檔案清單」 |
| 交付階段 | 整合所有修改，每個檔案只交付一次 |

### 19.2 整合交付原則

同一個檔案在討論中被提到多次修改時，AI 必須：
1. 收集所有修改項目。
2. 整合成一次修改。
3. 只交付一次。

**禁止**：同一個檔案交付兩次。

### 19.3 檔案狀態總表

每次有修改點時，AI 在回覆末尾顯示「檔案狀態總表」。

**狀態定義**：

| 狀態 | 標記 | 意義 |
|---|---|---|
| 討論中 | 💬 | 已記錄修改項，尚未確認交付 |
| 待交付 | ⏳ | 已確認，等待交付 |
| 已交付 | ✏️ | AI 已交付，等你更新 |
| 已更新 | ✅ | 你已貼到 GitHub |
| 方案已改 | 🔄 | 需重新交付 |
| 已廢棄 | 🗑️ | 不再使用 |

### 19.4 插話確認機制

當 AI 交付檔案後，若使用者**未明確說「已更新」就插話**，AI 必須先問：

> 剛才交付的 {檔案路徑}，請問是否已更新？
> A. 已更新
> B. 未更新
> C. 不確定
> D. 稍後再說

依使用者的回答處理：

| 回答 | AI 動作 |
|---|---|
| A | 標記 ✅，繼續後續 |
| B | 標記 ⏳，重新交付該檔案 |
| C | 標記 ⏳，重新交付該檔案 |
| D | 標記 💬，暫停交付，等使用者回來 |

**在使用者確認之前，AI 不得繼續交付下一個檔案。**

### 19.5 每 5 輪主動回顧

每 5 輪對話，AI 主動回顧「檔案狀態總表」，問使用者是否有遺漏。

### 19.6 交付前逐項確認

交付前，AI 列出完整清單，逐項確認每個檔案的修改項目。

### 19.7 中途交付規則

若使用者明確要求「先交付這個檔案」，AI 應：
1. 立刻交付。
2. 標記「這是中途交付」。
3. 後續如果有修改，仍會重新整合。
