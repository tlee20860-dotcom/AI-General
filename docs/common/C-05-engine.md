## 一、Token 管理與顯示（C-06 無損合併）

### 1.1 顯示規則

| Emoji | 剩餘 | 行為 |
|---|---|---|
| 🟢 | ≥ 50% | 正常交付 |
| 🟡 | 20~49% | 提示偏低 |
| 🔴 | < 20% | 提供新對話開場白 |

**顯示格式**：`Token: {emoji} 剩餘: {pct}%`（一律置於回覆末尾）。

### 1.2 用途與目標（C-06 §一）

| 項目 | 說明 |
|---|---|
| 問題 | AI 對 Token 剩餘量的估算不準確 |
| 解法 | 以公式計算為主，累積數據校正 |
| 目標 | 累積數據後校正估算，使誤差 < 20% |

### 1.3 估算原則（公式為主，C-06 §一點五）

**核心**：**無平台顯示，以公式計算為主**。

| # | 規則 |
|---|---|
| 1 | 一律以公式計算（§1.4）為主 |
| 2 | 若未來有 API `usage` → 優先採用 |
| 3 | 若未來有平台顯示 % → 優先採用 |
| 4 | 公式計算是目前唯一可用方法 |

**低於 20% 強制重估（D-102 修正）**：

| # | 規則 |
|---|---|
| 1 | 若公式估算 < 20% → 不得直接報告，必須重估 |
| 2 | 重估採不同方法（如：對話字數 vs 1M 窗口 / 累積輸入 / 累積輸出） |
| 3 | 重估後仍 < 20% → 才可報告 |
| 4 | 以「內容總量 vs 窗口」為主 |

### 1.4 參考公式（C-06 §二）

**DeepSeek 官方換算依據**：

| 類型 | 比例 |
|---|---|
| 中文 | 1 字 ≈ 0.6 Token |
| 英文 | 1 字元 ≈ 0.3 Token |
| 數字 / 符號 | 1 個 ≈ 1 Token |

**總量公式**：`總 Token = 輸入 Token + 輸出 Token`

**每行 Token（由官方比例推導）**：

| 檔案類型 | 每行 token |
|---|---|
| .md 表格 | ~18 |
| .md 敘述 | ~12 |
| .js 程式碼 | ~15 |
| .css | ~8 |
| .html | ~10 |
| .json | ~10 |

**對話輸入總量**：

> **輸入（累積） = k × N² / 2**

| 符號 | 說明 |
|---|---|
| k | 每輪平均新增 token |
| N | 對話輪數 |

**輸出總量**：

> **輸出 = 全部回覆的 token 總和**

**上下文窗口需求**：

> **窗口需求 = 全部上傳內容 + 全部回覆**

**DeepSeek-V4 窗口**：1M token

**計費總量**：

> **計費 ≈ 窗口需求 × 30~40 倍**

### 1.5 記錄格式（C-06 §三）

| 欄位 | 說明 |
|---|---|
| 批次 | 當前批次號 |
| 對話編號 | 本次對話的編號 |
| 對話輪數 N | 對話的總輪數 |
| 每輪平均新增 k | 全部上傳 + 回覆 ÷ N |
| 輸入累積 | k × N² / 2 |
| 輸出總量 | 全部回覆 token 和 |
| 窗口需求 | 上傳 + 回覆 |
| 窗口佔用 % | 窗口需求 / 1M |
| 估算剩餘 % | 100% − 窗口佔用 % |
| 實際狀態 | 使用者反饋 |
| 誤差 | 估算 % − 實際 % |
| 校正係數 | 下次估算乘數 |

### 5.2 對照組強制（最高優先）

**原則**：遇到「單一帳號、單一裝置、單一頁面」異常時，**必須先建立對照組**。

| 異常類型 | 對照組做法 |
|---|---|
| 單一帳號異常 | 用全新帳號（或無痕 + 新帳號）登入 |
| 單一裝置異常 | 換另一台裝置 |
| 單一頁面異常 | 訪問其他同類頁面 |

**判斷**：

| 對照組結果 | 結論 |
|---|---|
| 正常 | 100% 是原狀態快取卡死 |
| 也異常 | 系統級問題，繼續排查 |

### 5.3 路徑問題強制前置

任何涉及「檔案路徑 / 資料夾結構」的建議，**必須先查 docs**。

| 步驟 | 動作 |
|---|---|
| 1 | grep P-01 §十 + P-03 |
| 2 | 若未記載 → 先補 docs，再回答 |
| 3 | 若與實際不符 → 先提醒，再修正 |
| 4 | 禁止憑印象回答路徑 |

**新增（D-133）**：提到 repo 時，一律用實際名稱（見 R-01 §三之一）；禁止「Repo A / Repo B」代稱。

| 專案層 | 02-CORE-PROJECT.md + 90-{專案}.md |

**AI 讀到後**：

| 步驟 | 動作 |
|---|---|
| 1 | 回報共享包「構建編號」與「生成時間」 |
| 2 | 問使用者「是否為最新」 |
| 3 | 提示下一議題 |
| 4 | 列 4 選項（新專案 / 舊專案 / 純討論 / 其他） |
| 5 | 依情境處理 |

**若需其他分檔**：AI 依 C-02 §19.9 **主動提示上傳**（不得沉默不索取）。

### 5.7 新專案領域詢問流程（D-137）

**觸發**：使用者選「新專案」時。

| 步驟 | 動作 |
|---|---|
| 1 | **AI 先問領域** |
| 2 | 使用者回答（Web App / VBA / 資料分析 / …） |
| 3a | 已有領域 → 直接開新專案 |
| 3b | 新領域 → AI 主動建議建 `{X}-*` 6 檔 |
| 4 | 使用者確認 → 產出 6 檔草稿 |
| 5 | 依使用者回饋迭代 |
| 6 | **產出該專案 `notify.yml`** |

**6 檔模板**：見 C-00 §十一（舊引用；若新版無此節，依原模板）。

### 6.1 詞彙定義

| # | 詞彙 | 定義 |
|---|---|---|
| 1 | 啟動包 | 新對話時，使用者上傳給 AI 的第一個（或第一組）共享包。現制為：體系層上傳 `01-CORE-SYSTEM.md`；專案層上傳 `02-CORE-PROJECT.md` + `90-{專案}.md`。 |
| 2 | 共享包 | 由 Actions 自動生成、放在 `AI-packages` 的檔案。 |
| 3 | 專案包 | 每個專案專屬的共享包，如 `90-web-app-family.md`。 |
| 4 | 核心包 | 分為「體系層核心包」（`01-CORE-SYSTEM.md`）與「專案層核心包」（`02-CORE-PROJECT.md`）。 |
| 5 | 專案清單 | 已併入 `STATE-INDEX.md` §一（原名 `PROJECT-LIST.md`，已廢除）。 |
| 6 | 倉庫清單 | 見 `setup-structure.yml` 頂部 `PROJECT_REPOS`（SSOT）。 |
| 7 | 對話編號 | 格式 `{專案代碼}-{YYYYMMDD}-{專案內序號3位}`。 |
| 8 | 回覆序號 | 格式 `#{序號}`，同一對話內每次回覆遞增。 |
| 9 | 交付前確認 | AI 必須先報告「打算做什麼」，等使用者確認後才輸出完整內容。 |
| 10 | 自主提取協議 | AI 收到需求後，自動從共享包中找出相關檔案，不需詢問「要讀取哪些檔案」。 |
| 11 | 分步讀取協議 | 每次最多讀取 2 個檔案；若需其他分檔，AI 必須主動提示使用者上傳。 |
| 12 | 四倉架構 | `AI-General`（體系層）、`AI-packages`（生成層）、各專案倉庫、`AI-training-files`（歷史，已停用掃描）。 |
| 13 | 生成時間戳 | 每個共享包頂部的 `YYYY-MM-DD HH:mm:ss UTC`。 |
| 14 | 領域 | 專案的分類，例如 W（Web App）、V（VBA）、D（資料分析）。 |
| 15 | 專案交接檔案 | 每個專案專屬的 `P-13-handoff.md`。 |
| 16 | Q 編號 | 問題的編號，格式 `Q{數字}`。 |
| 17 | D 編號 | 決策的編號，格式 `D-{數字}`。 |
| 18 | 人話說明 | 選項下方用「> 人話解釋：」開頭的一行說明。 |
| 19 | 所屬專案 | 每個檔案、修改方案、交付內容所屬的專案名稱。通用檔案標「AI 對話系統」，專案檔案標對應專案。 |
| 20 | 交付類型 | 每個交付檔案的類型：新增、修改、刪除。 |
| 21 | 檔案狀態總表 | 一張表同時記錄「待交付」與「已交付」的檔案狀態。 |
| 22 | 整合交付 | 同一個檔案的多項修改，整合成一次交付，禁止重複交付。 |
| 23 | 插話確認 | 交付檔案後，若使用者未明確說「已更新」就插話，AI 必須先確認該檔案狀態。 |
| 24 | 先收集後交付 | 討論階段只記錄修改點，不交付；確認階段才列清單；交付階段才執行。 |
| 25 | 專案代碼 | 用於對話編號前綴的英文代碼，由 `STATE-INDEX.md` 的 `code` 欄位決定。例如 `webapp`、`ai-system`。 |
| 26 | 專案內序號 | 該專案的第幾個對話，從 `001` 開始，跨日期累計。不同專案各自獨立。 |
| 27 | 構建編號 | 共享包頂部的 `#NNNN`，由 Actions 的 `run_number` 產生。AI 讀到後須回報並問使用者是否最新。 |
| 28 | 包編號 | 共享包的編號，十位數 = 類別（01 體系 / 02 專案 / 10+ 領域 / 90+ 專案 / 99 罕用）。 |
| 29 | 體系層結論 | `SYSTEM-CONCLUSION.md`，體系層滾動式累積結論（議題 + 決策）。 |
| 30 | 體系層交接 | `SYSTEM-HANDOFF.md`，體系層交接快照（≤ 80 行）。 |
| 31 | STATE-INDEX | `STATE-INDEX.md`，由 Action 掃描生成的體系狀態索引（專案總覽 + 檔案清單 + 歷史歸屬），取代舊 R-01、PROJECT-LIST、FILE-INDEX。 |
| 32 | 源檔分檔 | C-* / P-* / W-* 保持各自獨立，不合併；由 Action 在生成共享包時負責合併。 |
| 33 | 兩階段確認 | 交付檔案時，先問「確認完整」，收到回覆後才提示貼上；貼上後回「已更新」才算完成（D-162）。 |
| 34 | PROJECT_REPOS | `setup-structure.yml` 頂部的專案清單（含 repo），新增專案時由此處更新。 |
