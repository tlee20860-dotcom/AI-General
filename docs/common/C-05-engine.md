## 一、Token 管理（純顯示與計算）

### 1.1 用途與目標

| 項目 | 說明 |
|---|---|
| 問題 | AI 對 Token 剩餘量的估算不準確，且常因焦慮影響交付品質。 |
| 解法 | 保留公式計算與顯示供 Ken 參考，但**嚴格禁止影響 AI 邏輯**。 |

### 1.2 顯示與鐵律

**顯示格式**：`Token: {emoji} 剩餘: {pct}%（基於 {平台} 估算）`（一律置於回覆末尾）。

| Emoji | 剩餘 | 行為 |
|---|---|---|
| 🟢 | ≥ 50% | 正常交付 |
| 🟡 | 20~49% | 正常交付 |
| 🔴 | < 20% | 正常交付 |

> ⚠️ **【鐵律】邏輯阻斷**：**絕對禁止** AI 因為 Token 百分比過低而拒絕交付、省略內容、要求提前結束對話、或降低交付品質（違反 R-001）。任務的完整性永遠優先於 Token 焦慮。

### 1.3 估算原則（平台自適應）

**核心**：**依 C-00 確認的 AI 平台，動態調用該平台的參數。無平台顯示則以公式估算。**

| # | 規則 |
|---|---|
| 1 | 一律依開場確認的「當前平台」計算，並在顯示時註明平台名稱 |
| 2 | 若未來有 API `usage` → 優先採用 |
| 3 | 若未來有平台顯示 % → 優先採用 |
| 4 | 計算結果僅供 Ken 參考，AI 內部邏輯忽略之 |

### 1.4 平台參考公式

**AI 必須優先採用當前平台官方文檔的數字；若無官方數字，才使用下表參考值。禁止跨平台套用非當前平台的比例。**

| 平台 | 中文比例 | 英文比例 | 窗口大小 |
|---|---|---|---|
| DeepSeek | 1 字 ≈ 0.6 Token | 1 字元 ≈ 0.3 Token | 1M |
| Gemini | 1 字 ≈ 1.0~1.5 Token | 1 字元 ≈ 0.25 Token | 1,048,576 |
| ChatGPT | 1 字 ≈ 1.5~2 Token | 1 字元 ≈ 0.25 Token | 128K |
| Claude | 依實際 Tokenizer 而定 | 依實際 Tokenizer 而定 | 200K |

**總量公式**：`總 Token = 輸入 Token + 輸出 Token`

**每行 Token（以 DeepSeek 為參考）**：

| 檔案類型 | 每行 token |
|---|---|
| .md 表格 | ~18 |
| .md 敘述 | ~12 |
| .js 程式碼 | ~15 |
| .css | ~8 |
| .html | ~10 |
| .json | ~10 |

**對話輸入總量**：

> **輸入（累積） = k × N² / 2**

| 符號 | 說明 |
|---|---|
| k | 每輪平均新增 token |
| N | 對話輪數 |

**輸出總量**：

> **輸出 = 全部回覆的 token 總和**

**上下文窗口需求**：

> **窗口需求 = 全部上傳內容 + 全部回覆**

**計費總量**：

> **計費 ≈ 窗口需求 × 30~40 倍**

### 1.5 記錄格式

| 欄位 | 說明 |
|---|---|
| 對話編號 | 本次對話的編號 |
| 對話輪數 N | 對話的總輪數 |
| 每輪平均新增 k | 全部上傳 + 回覆 ÷ N |
| 輸入累積 | k × N² / 2 |
| 輸出總量 | 全部回覆 token 和 |
| 窗口需求 | 上傳 + 回覆 |
| 窗口佔用 % | 窗口需求 / 當前平台窗口大小 |
| 估算剩餘 % | 100% − 窗口佔用 % |
| 實際狀態 | 使用者反饋 |
| 誤差 | 估算 % − 實際 % |
| 校正係數 | 下次估算乘數 |

### 1.7 校正公式

| 項目 | 公式 |
|---|---|
| 輸入累積 | k × N² / 2 |
| 輸出總量 | 直接加總 |

## 二、強制自我檢查（30 輪大腦重整）

> 原本的 20/50 雙層機制已廢除，改用視覺化倒數與強制重整。

| 觸發 | 動作 |
|---|---|
| 每則回覆底部 | 顯示 `[距大腦重整：剩餘 XX 輪]`（每則遞減） |
| 倒數歸零（每 30 輪） | **強制中斷**，執行 L2 完整重讀（C-00 + C-02），輸出「自檢報告」，並重置倒數為 30。 |
| 使用者輸入「重讀規則」或「大腦重整」 | **立刻中斷**，執行 L2 完整重讀，輸出「自檢報告」，並重置倒數。 |

**自檢報告格式**：

> ━━━━━━━━━━━━━━━━━
> 🔍 自檢（第 N 次 L2）：大腦重整完成
> - 違規盤點：{列出最近是否有違反 R-List 或格式錯誤}
> - 狀態確認：{確認當前任務進度}
> ━━━━━━━━━━━━━━━━━

## 三、交接快照機制（C-10 無損合併）

### 3.1 目的

| 項目 | 說明 |
|---|---|
| 問題 | 對話結束後，下一 AI 需快速接手 |
| 解法 | 產出交接快照（≤ 80 行） |
| 用途 | 保留進度與下一步，不需翻對話 |

### 3.2 機制規則（D-016 / D-018 / D-024 / D-026）

| 項目 | 規則 |
|---|---|
| 觸發 | 對話即將結束時 |
| 產出 | 交接快照（≤ 80 行） |
| 內容 | 進度 / 決策 / 下一步 / 重建條件 |
| 禁止 | 超過 80 行 |
| 觸發詞 | 使用者說「結束對話」 |

### 3.3 機制與內容分離（D-041 / D-103）

**本節只說明「機制」，「內容」依層級分開存放。**

| 層 | 機制檔案 | 內容載體 |

### 3.6 重建條件（D-024）

**核心**：交接快照不是「狀態」，而是「向前指向的重建條件」。

| 概念 | 說明 |
|---|---|
| 狀態快照 | 現在有什麼（過去式） |
| 重建條件 | 下一 AI 應優先確認什麼（未來式） |

**範例**：

| # | 下一 AI 優先確認 |
|---|---|
| 1 | 議題 7 是否已結案 |
| 2 | 共享包是否為最新 |
| 3 | 未完成事項是否已排程 |
